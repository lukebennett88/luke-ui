# Theme colour generation (v2)

This explains how `theme/build-theme.ts` generates colour and what changed when the private 12-step
scale engine (`scale.ts`, `surfaces.ts`, `semantic-map.ts`) replaced the original per-token colour
solver. Read [STYLING.md](STYLING.md) first for the theme module layout.

## The pipeline

Per colour mode, `compileTheme` (in `build-theme.ts`):

1. Takes the already-resolved source colours and base surface (`surface.base`, split from
   `neutral`'s hue/chroma character in `define-theme.ts`), plus any surface the author set. Source
   colours cross the foundation as OKLCH values. `defineTheme` applies defaults and parses authoring
   strings once before `buildTheme` runs.
2. Computes `text.primary` from the resolved neutral source (`highContrastText`, the family's
   step-12 rung) before any solid-anchor search, then generates the six private 12-step OKLCH
   families (`neutral`, `accent`, `info`, `success`, `warning`, `danger`). Every family is
   accessibility-gated against that same `text.primary`.
3. Resolves the four surfaces (`base`/`subdued`/`field`/`overlay`) with `surfaces.ts`'s
   `generateSurfaces`. `base` and any authored surface pass through as written. Each missing surface
   is a fixed, mode-specific lightness offset from `base`, never from a sibling. Surfaces are never
   adjusted for contrast. Validation throws instead, and the author can set the surface.
4. Solves `border.control` against all four surfaces (`control-border.ts`), and derives
   `border.controlHover` from it by a fixed per-mode lightness offset.
5. Fits each role's translucent subtle fill (`subtle-fill.ts`'s `generateSubtleFill`) against the
   resolved surfaces. See [Translucent subtle fills](#translucent-subtle-fills).
6. Applies the one default semantic mapping (`semantic-map.ts`'s `mapSemanticColors`) that aliases
   every colour contract leaf onto a family step, a generated surface, a generated interaction
   state, or a subtle fill, and passes the authored backdrop through. Neutral step 12 becomes
   `text.primary`.
7. Runs the full WCAG 2.2 validation matrix (`validateContrast`), which stays authoritative and
   throws `ThemeContrastError` on a hard-gate miss. Validation measures semantic token relationships
   using final emitted, rounded, and gamut-mapped colours. A translucent subtle fill is measured as
   it paints over `surface.base`. Both global text hierarchy colours are checked against every
   standard surface and all 18 subtle backgrounds. All six roles' three foreground states are
   checked against every standard surface and all 18 subtle backgrounds (324 subtle pairs per mode).
   Both `onSolid.primary` and `onSolid.secondary` are checked against their role's solid rest,
   hover, and pressed fills. The two on-solid leaves initially emit the same literal resolved
   colour. New cross-role failures are rejected without automatic repair.

`compileTheme` returns `{ css, diagnostics }`. `ThemeDiagnostics` records everything the pipeline
resolved (both modes' families, surfaces, solid-anchor search, subtle fills, and contrast checks)
for tooling.

## The v2 repaint is expected

v2 regenerates every colour token from the private scale instead of solving each token
independently, so **every generated colour value can move**, even where the previous solver's result
looked visually similar. This is a property of switching generators, not a regression in any one
token.

Theme output is protected by the contrast, scale, semantic-map, and stylesheet contract unit tests,
plus the token-board visual captures across the fixture themes and modes. A generator change that
repaints colours should show up there and in visual review. The pre-v2 output is recoverable from
git history (commit `cef0076`) and is not committed.

## Private ≠ non-breaking

A change to the private generator (`scale.ts`, `surfaces.ts`, `semantic-map.ts`) repaints every
generated colour, even though none of it is public API. Review those unit tests and the token-board
visuals when a generator change intentionally repaints. Generator **versioning** (a version stamp
threaded into the stylesheet header) is a deliberately deferred v1 concern — the stylesheet header
stays the plain `/* Generated by buildTheme from @luke-ui/react. Do not edit. */` line for now.

## The dropped `resting` colour surface

The pre-v2 solver generated and validated against a hidden, unemitted `resting` colour rung that had
no public semantic meaning. v2 drops it: colours are validated only against surfaces a consumer can
actually reference (`base`, `subdued`, `field`, `overlay`), which changes the contrast matrix from
the pre-v2 solver's.

`depth.resting` is unrelated and unaffected — it is a **material** (box-shadow) concept in the depth
ladder, not a colour surface, and the depth ladder did not change.

## Border contrast policy

WCAG 2.2 SC 1.4.11 requires 3:1 contrast only for visual information required to identify a
component or state, not every authored border, so v2 splits border tokens into hard gates and an
advisory group. Every gate covers all four surfaces: forms, links, and semantic text appear on
`subdued` regions as well as on `base`, `field`, and `overlay`.

- `color.border.control` is a hard gate. It is a dedicated contrast boundary, not a scale-step
  alias, and must reach ≥3:1 against every surface in both modes. It is frequently the sole resting
  boundary of a form control, so it cannot use the softer step-7 aesthetic.
- `color.border.controlHover` is a hard gate against the same surfaces. It is `border.control` moved
  by a fixed, tuned lightness offset toward more contrast. There is no search and no rule that hover
  must exceed rest: the guarantee is 3:1, and how distinct hover looks is a visual decision.
- `color.background.danger.solid.rest` is also a hard gate against every surface. It is the only
  role fill that carries a required state's boundary (the invalid field boundary —
  [#247](https://github.com/lukebennett88/luke-ui/issues/247)), so it needs the same guarantee as
  `border.control`. This is deliberately not extended to the other five roles: a role's solid anchor
  is solved for 4.5:1 on-solid text, not for 3:1 against the surface behind it, and `warning` lands
  well under 3:1 in light mode.
- `color.border.focus` is a hard gate against all four surfaces. The keyboard-focus ring stays
  build-time validated at ≥3:1.
- `color.border.decorative` is not checked. It is a deliberately subtle, Radix-style separator below
  3:1.
- Every semantic role border (`color.border.<role>`, all six roles) is a decorative tint with an
  advisory 3:1 check. A miss does not gate the build.

Component invariant (tracked separately,
[#247](https://github.com/lukebennett88/luke-ui/issues/247)): any component that uses an advisory
border as the sole cue for a required state (invalid, selected, checked) must add another 3:1 or
non-colour cue: error text or an icon, a border-thickness or shape change, or a separately gated
indicator. Advisory borders are not guaranteed to be visible enough on their own.

## Accent policy

Accent adaptation is forgiving but never sacrifices the AA on-solid guarantee:

- A single-value accent (`accent: '#...'`) is pre-adapted by `defineTheme`'s `adaptAccent` into an
  accessible vibrant band before the scale generator sees it. The pre-conditioner calls the same
  `passesOnSolidGate` function the generator uses, with the same `text.primary`.
- An explicit per-mode accent (`accent: { light, dark }`) is used verbatim because the author has
  chosen its lightness. If its whole tone band has no lightness where near-white or near-black
  on-solid text clears AA, `compileTheme` throws `ThemeGenerationError` naming the failing role and
  mode.

## One gate for on-solid contrast

`scale.ts`'s `passesOnSolidGate` is the only function that decides whether a solid can carry
readable text. It asks whether the near-white or near-black on-solid colour the generator would
choose clears the AA text ratio plus the search headroom across the public solid rest, hover, and
pressed colours.

`defineTheme`'s `adaptAccent` pre-conditioner calls that same function rather than keeping its own
copy. Any lightness it accepts also passes the generator's solid-anchor search, and the generator
emits the accent it picks.

The pre-conditioner is necessary because its adaptation band is deliberately wider than the
generator's tone-faithful window. It can rescue accents, such as a mid-lightness red, that the
generator alone would report as unsatisfiable. Both searches walk the same lightness candidate grid.

`contrast-policy.ts` declares the shared thresholds: the 4.5 text ratio, the 3:1 non-text ratio, the
search headroom, and the search step. `lightness-candidates.ts` is the one grid those searches walk.
It also declares `SEMANTIC_ROLES`, the one canonical role list used by family generation, the
semantic map, and the validation matrix.

## `loadingSkeleton`

`color.loadingSkeleton` maps to the neutral family's step 8, for better perceptibility of the
loading state against typical surfaces.

## Interaction states

Hover and pressed colours are public semantic tokens, generated at theme compile time. Hover mixes
the resting colour 5% toward `text.primary` in OKLab. Pressed mixes it 10% toward the same target.
Those strengths are fixed. If a solid cannot carry readable on-solid text across the three states,
the solid-anchor search adapts the resting colour rather than changing the mix strengths. For subtle
fills, these mixes produce the opaque colours the translucent fill reproduces over `surface.base`.

Recipes select those tokens. They do not emit `color-mix()` or call a runtime helper. Theme authors
do not author hover or pressed colours, or a subtle fill's tint or alpha. There is no public overlay
hover, pressed, or tint API. `color.overlay.backdrop` is the authored modal dimming layer.
`color.surface.overlay` is the opaque surface for detached content such as menus, popovers, and
dialogs.

`validateContrast` measures the emitted token pairs. It does not catalogue first-party components.

## Translucent subtle fills

Every role's `color.background.<role>.subtle.{rest,hover,pressed}` is translucent in both modes: one
tint colour per role, at a rising alpha per state. An opaque fill tuned against `surface.base`
crosses a surface that is lighter or darker than `base`. In dark mode, `overlay` sits 0.07 above
`base`, so an opaque hover landed on the overlay itself. A translucent fill moves every surface by
nearly the same amount, so a state reads the same on `base`, `subdued`, `field`, and `overlay`.

`generateSubtleFill` derives the tint and alphas per theme, mode, and role:

1. Its targets are the opaque colours the role would otherwise emit: the family's subtle rung, and
   that rung mixed toward `text.primary` for hover and pressed.
2. Browsers composite a translucent colour by blending gamma-encoded sRGB channels, so every
   composite of one tint over `base` lies on a straight line in that space. The fit takes the
   least-squares direction of the targets' offsets from `base` and places the tint where that line
   leaves the sRGB cube. The most distant tint needs the least alpha, which keeps the fill's effect
   nearly the same on every surface.
3. Each state's alpha, on the three-decimal grid the stylesheet emits, is the one whose composite
   over `base` matches the target's OKLab lightness, with OKLab distance breaking ties. Text
   contrast follows lightness, so chroma carries the residual.
4. A state whose step from the state below it (or from the bare surface, for rest) is under
   `SUBTLE_FILL_MIN_STEP` on any standard surface has its alpha raised until it clears. Every state
   paints the same tint at a higher alpha, so rest, hover, and pressed stay ordered by distance from
   every surface.

All differences are OKLab distances. `contrast-policy.ts` declares the minimum step the generator
keeps, the calibrated floor the shipped and fixture themes must clear in tests
(`SUBTLE_FILL_STEP_FLOOR`), and the residual those tests accept over `base`
(`SUBTLE_FILL_MAX_RESIDUAL`). A custom theme below the floor compiles. The diagnostics report it.

A single tint gains chroma as its alpha rises, while the opaque hover and pressed colours lose it,
so chromatic roles cannot reproduce today's colours exactly. Neutral matches to within 0.006. The
shipped chromatic roles miss by up to 0.03, mostly at rest, with lightness within 0.001. The
diagnostics record each role's tint, alphas, residuals, any raised state, every composited layer,
and any step below the floor. They hide no compromise.

Validation of the composited result over the other surfaces, over stacked fills, and over solid
fills, including the state-order gate, belongs to
[#916](https://github.com/lukebennett88/luke-ui/issues/916).
