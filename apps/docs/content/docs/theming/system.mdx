title: Theme system

A Luke UI theme has four related parts. The theme root carries the shared reset. An identity
supplies the semantic values on that root: colour, type, spacing, radius, and depth. A colour mode
chooses the light or dark side of those values. A nested scope changes mode, or starts a new root,
for one part of a page.

This page explains how the four parts relate. Read [Applying a theme](/theming/applying) for the
exact classes and import steps, and [Colour modes](/overview/color-mode) for the mode contract in
full.

## The theme root and identity

Every themed subtree starts at one root element. The root carries `themeRootClassName` and one
identity class, such as `tactileThemeClassName`. `themeRootClassName` supplies the reset and the
base theme layer. The identity class supplies the semantic values for that subtree.

Luke UI ships two identities. Tactile is the default. It uses stronger depth and a compact material.
Paper is flatter, with lighter borders and depth.

An identity class does not nest. Give an application, or an independent part of a page, exactly one
identity class on its root. A part of a page that needs a different identity becomes its own root,
placed beside the first, never inside it.

## Colour mode

Each identity supplies light and dark values for every token. Colour mode chooses between them. Omit
`data-color-mode` to follow the reader's system setting. Set it to `light` or `dark` on any element
to force a mode for that element and its descendants.

Unlike identity, colour mode nests. A descendant element can carry its own explicit
`data-color-mode`, and only that part of the page changes mode. The identity stays the same
throughout. Only the light and dark values switch.

An explicit mode also sets the native `color-scheme` property, so browser-drawn controls such as
scrollbars match the surrounding content.

## Nested scopes

Put the two rules together. Colour mode nests freely. Identity does not. One themed page can carry a
single identity throughout, with as many nested colour-mode scopes as the design needs: a dark page
with a light embedded document, or a light preview inside a dark editor. A second identity always
needs its own root, placed beside the first scope in the DOM.

## Portalled UI

A portal, such as a popover or a dialog, often renders outside its trigger's DOM branch, close to
the document body rather than inside the themed subtree. A CSS custom property set on the themed
root does not reach across that gap. The portal root needs its own copy of the active identity class
and any explicit colour mode. Leave the colour-mode attribute off the portal root when the trigger
follows the system setting, so the portal follows the system setting too.

Luke UI's Combobox carries this contract to its own popover. It reads the trigger's identity class
and colour-mode attribute when the popover opens, and applies the same values to the popover root.
An application-owned portal needs to copy the same two values itself.

## Best practices

| Guidance | Practice                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------- |
| Do       | Give one themed subtree one identity class, and start a new root for a second identity.             |
| Do       | Copy the trigger's identity class and any explicit colour mode onto a portal root.                  |
| Don't    | Nest a second identity class inside a subtree that already has one.                                 |
| Don't    | Leave a portal without the trigger's identity class, even when the mode follows the system setting. |
