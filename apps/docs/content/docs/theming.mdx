title: Theming
description: Understand how the theme root, identity, colour mode, and tokens fit together.

A theme supplies the semantic values used by Luke UI components and custom UI. It is static CSS and
does not change component behaviour.

## Theme foundations

Every themed subtree has one theme root, rendered by `Theme` with a `name`. It carries the reset,
the base theme layer, and one identity class.

The identity class supplies the semantic token values used by components and custom UI. Each
identity includes light and dark colour values. The active colour mode chooses between them. An
explicit colour mode is optional. Without one, the theme follows the system preference.

Colour-mode scopes nest within an identity: a `Theme` without `name` changes only the colour mode of
the enclosing identity. Identities do not nest. A `Theme` with a `name` inside another one resolves
against the outer identity's values at equal precedence, so the result depends on stylesheet order.
Use a separate theme root, outside the first, for a subtree that needs another identity.

Read [Applying a theme](/applying-a-theme) for the exact imports, props, and colour-mode rules.

## Component variants

Components define the choices available within the theme. For example, Button owns its tone,
appearance, size, and interaction behaviour. The theme supplies the semantic values behind those
choices.

```tsx
<Button appearance="solid" tone="accent">
	Save changes
</Button>
```

Prefer component props over custom CSS. Author a theme when the product needs a different visual
foundation across the system.

## Semantic tokens

The active theme exposes a typed, public `vars` contract. Use it when a custom element sits beside
Luke UI components.

Read [Token reference](/token-reference) for the full contract. Read [Colour](/color) for the
semantic roles it exposes.
