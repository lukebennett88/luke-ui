Luke UI names colours by their job. A theme maps those roles to values for each identity and colour
mode. A component then stays consistent, because it does not need to know the underlying palette.

## Surfaces and content

Surface roles describe where an element sits in the interface:

- `color.surface.base`: the default page and control background.
- `color.surface.subdued`: secondary regions, such as a sidebar or a panel set apart from the page.
- `color.surface.raised`: elevated panels, cards, menus, popovers, and dialogs. This is an opaque
  colour shared by inline and detached content.

`color.overlay.backdrop` dims content behind a modal. It is not a surface colour.

Choose borders and depth separately. A raised surface does not add either, and flat cards can use
`base` with a border or `subdued`.

Text uses `primary` and `secondary` roles. Borders distinguish decorative, control, and focus uses.
Text, role foregrounds, `color.border.control`, `color.border.danger`, and the focus ring are
guaranteed to contrast with all three surfaces. Control hover and pressed borders derive from
`color.border.control` and keep the same contrast guarantee. `color.border.decorative` is a
separator with no contrast guarantee.

```tsx
import { vars } from '@luke-ui/react/theme';

<section
	style={{
		backgroundColor: vars.color.surface.subdued,
		borderColor: vars.color.border.decorative,
		color: vars.color.text.primary,
	}}
/>;
```

Choose the role that describes the element's purpose. Do not copy a resolved colour into application
CSS. It will not adapt when the identity or colour mode changes.

## Semantic roles

Six roles cover the meanings a component needs beyond plain surfaces and text: `neutral`, `accent`,
`info`, `success`, `warning`, and `danger`. All six provide the same background, foreground, and
border tokens. Choose a role for what the colour communicates:

- `neutral`: no accent or status meaning, distinct from ordinary surfaces.
- `accent`: preferred, selected, or emphasised. Not a promise of a brand colour.
- `info`: noteworthy factual context.
- `success`: completed, valid, or a positive result.
- `warning`: needs attention but has not failed and is not dangerous.
- `danger`: harm, failure, invalidity, or a critical condition.

Select a role to compare the same semantic token pairs in light and dark mode. The notice content
stays constant, so only the role and mode change its colours.

### Background and foreground

Each role has a resting `subtle` background and a `solid` background with `rest`, `hover`, and
`pressed` states. Adaptive hover and pressed feedback uses the shared interaction tint pair:

```tsx
import { vars } from '@luke-ui/react/theme';

vars.color.background.warning.subtle.rest;
vars.interaction.tint.hover;
vars.interaction.tint.pressed;
vars.color.background.warning.solid.rest;
vars.color.background.warning.solid.hover;
vars.color.background.warning.solid.pressed;
```

Use a role's `rest`, `hover`, and `pressed` foreground on any standard surface or any role's subtle
background. Use `onSolid.primary` or `onSolid.secondary` on that role's solid backgrounds:

```tsx
vars.color.foreground.warning.rest;
vars.color.foreground.warning.hover;
vars.color.foreground.warning.pressed;
vars.color.foreground.warning.onSolid.primary;
vars.color.foreground.warning.onSolid.secondary;
```

`onSolid.primary` and `onSolid.secondary` each reach at least 4.5:1 against `solid.rest`,
`solid.hover`, and `solid.pressed`. Both currently resolve to the same literal colour. Secondary
guarantees an accessible selection on the solid background, not visible de-emphasis.

Built-in controls select these tokens for hover and pressed. Custom interactive elements should do
the same.

### Borders

Each role also has one state-free border, for example `vars.color.border.warning`. The token
describes meaning. The component decides when to apply it, such as only while invalid or as a
permanent outline.

`color.border.danger` marks an invalid control's boundary and reaches at least 3:1 against all three
standard surfaces in both modes. Use it for invalid borders and outline edges. Danger solid
backgrounds carry the on-solid text guarantee, but have no 3:1 guarantee against those surfaces.

The other five role borders are decorative tints, for example on an application notice. Luke UI
measures their contrast, but does not guarantee they reach 3:1. See
[contrast validation](/docs/authoring-a-theme#contrast-validation). Never rely on one alone to
communicate a required state such as selected, invalid, or checked. Pair it with text, an icon, or
another cue that is separately contrast-gated. Use `color.border.control` when a custom element
needs a guaranteed boundary.

### The numeric scale is private

Behind each role, the theme generator builds a numeric colour scale. It is not emitted as CSS and
has no public token. Use the semantic roles in your application, and use `defineTheme` with source
colours to author a theme.

## Text on a background

A Luke UI background sets the text colour for everything inside it. A `Box` with `backgroundColor`
is one. So are the surfaces components paint, such as a Button fill, a field, a popover, and a code
chip. Each sets the text colour to its readable primary, which an `Icon` inside inherits, and tells
`Text` and `Heading` inside it which colours are readable:

| Background               | `primary` and `secondary`                     | A role, such as `color="danger"` |
| ------------------------ | --------------------------------------------- | -------------------------------- |
| A surface, `surface.*`   | `text.primary` and `text.secondary`           | The role's foreground            |
| Any role's `subtle` fill | `text.primary` and `text.secondary`           | The role's foreground            |
| A role's `solid` fill    | That role's `onSolid.primary` and `secondary` | That role's `onSolid.primary`    |

A role keeps its hue on another role's subtle fill. The theme compiler checks every pairing in the
table at 4.5:1 in both colour modes, and a theme that misses one does not compile. Pairings outside
the table are not checked, such as disabled text and text on a background from your own CSS. A
nested background sets a new context. A `Box` without `backgroundColor` keeps the surrounding one.
An element with `data-color-mode` sets the context again in its own mode.

`Box` takes each role's resting `subtle` and `solid` fill. Interactive components own the hover and
pressed fills and pair them for you.

### Custom surfaces

To make a custom element a Luke UI background, set `backgroundColor` on a `Box` that also carries
your class. Put both on the same element rather than wrapping one in the other.

```tsx
<Box backgroundColor="accent.solid" className={styles.card}>
	<Heading>Example heading</Heading>
	<Text>Inherits the fill's readable colour.</Text>
</Box>
```

A background from your own CSS, such as `vars.color.background.accent.solid.rest`, sets no text
colour and does not change which colours `Text` reads. Nor does an image, a gradient, a translucent
colour, or CSS that overrides a `Box` background. Luke UI does not detect whether a background is
dark. Set the text colour in the same CSS and check its contrast yourself.

## Disabled and loading states

Use the component's disabled or loading API when it has one. Those states account for interaction
and accessibility as well as colour. Disabled is a state, not a palette: interactive controls fade
with reduced opacity, and only field text recolours, through the public `text.disabled` role. On a
solid fill, disabled field text uses the fill's `onSolid.secondary` instead. The public
`loadingSkeleton` role is available when you build an equivalent custom element.
